# 倒计时接口对照数据集

两套数据集共用 120 条 query、样本编号和参考日期，完整语料及期望均已包含在各自目录内，按
`request_baseline/Q001.json` 的请求结构补齐公共字段，可在当前工作区直接批跑。

| 数据集 | 固定日期接口 | 周期规则接口 | 样本总数 |
| --- | ---: | ---: | ---: |
| countdown_fixed | 120 | 0 | 120 |
| countdown_recurring | 30 | 90 | 120 |

## 配对与差异边界

- Q001—Q030：确定日程，两组均使用 `GetCountdownDays`，完整请求内容相同。
  Q012、Q013 保留过去日期和负天数语义，不强行套用只返回非负天数的周期接口。
- Q031—Q060：每周三；固定组绑定参考日解析出的具体日期，周期组使用 `* * 3 *`。
- Q061—Q090：每月最后一个周六；周期组使用 `* * 6L *`。
- Q091—Q120：公历周年纪念日；周期组使用 `日 月 * *`，不带历史起始年。
  2月29日采用 `29 2 * *`，跳过不存在该日期的年份。

周期规则严格采用指定注册表的“日 月 星期 年”四字段格式。
接口定义来源：
`widget_service/cloud/data/capabilities/app-11.7.7.300_rom-7.0/data_capabilities.json`。

同编号样本仅允许以下字段不同：

1. `content.candidateDataBindings[0].capabilityId` 与外层镜像。
2. `content.candidateDataBindings[0].arguments` 与外层镜像。

其余完整请求字段逐值相同：query、title、description、size、候选素材、交互候选、
设备信息、参考时间、会话信息、用户信息、协议版本和原始语料均一致。
两组都将结果写入 `/data/countdown`，仅选择 `/countdownDays`，
避免写入路径及额外输出字段影响生成效果。周期接口的默认写入路径不是必选限制；
这里显式指定公共路径，不引入额外日期输出这一展示变量。

## 公共字段与素材

请求外层字段集合和 `content` 字段集合均与 `request_baseline` 模板一致，
所有外层同名业务字段镜像 `content`。设备公共字段沿用基线模板，
包括 App 版本 `11.9.9.342`；时间保留每条源样本的参考日北京时间09:00。
每条的 query、标题、说明与尺寸沿用源样本，2x2、2x4 各60条。
会话信息按编号固定，成对样本完全相同；批跑入口会在请求副本中覆盖运行身份。

全部样本提供已登记的 `asset.stopwatch_fill` 与 `asset.calendar_fill`，
周年纪念日样本额外提供 `asset.cake_fill`。两组素材列表及顺序相同。
源语料没有要求可执行跳转或通知，交互候选统一为空，不额外添加动作。

## 标注与验收

- `Q001.json`—`Q120.json`：批跑请求。
- `evaluation/expectations.json`：两组共用的逐条标注，包含源语料、规则、参考日、
  目标日期、天数、两种入参及是否属于90条接口比较样本；两份文件内容相同。
- `version.json`：v1 初始版本，历史为空。
- 本说明在两组中内容相同。

`expectedTargetDate`、`expectedCountdownDays` 是在逐条参考日下的测试期望，
不是伪造的实时输出，也不能代替端侧结果。核对这些值时须使用相同的测试日期与时区；
仅传入 `deviceInfo.time` 不等于冻结端侧系统时钟。
0天包含今天；月末周六取最后一次周六，不固定为第四周；闰日不折算为其他日期。

固定组的周期语料有意使用创建时解析的具体日期，作为旧接口对照；
它不能据此证明长期周期刷新已满足。周期组保留规则，由端侧在刷新时求下一次日期。
单次创建效果、日期语义和跨周期刷新应分别评审，不以云侧生成成功替代真机验收。
统计接口差异时使用90条周期样本，30条一次性样本用于共同对照。

成对运行应保持服务版本、生成路线、模型、重试、主题和其它公共配置一致。
参考日的两个接口应得到相同天数；跨周期后的结果差异来自接口语义，不应回填固定组日期。
